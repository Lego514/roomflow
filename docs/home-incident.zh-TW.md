# 居家案例：反覆延遲平台與 IPv6 結果缺失

[English](home-incident.md) · [去識別化證據](evidence/home-incident.json)

**狀態：已核對觀察資料，根因與居家改善尚未確認。** 本案例描述已保存的探測結果，並非已驗證的 Zoom／Teams 故障。閘道中位數低、外部目標較慢，或 lab 結果，單獨都不能確診 bufferbloat、指出某台裝置或證明 ISP 故障。

## 觀察範圍與資料來源

固定範圍為 **2026-10-07 18:47:19 UTC 至 2026-10-12 06:05:02 UTC**，含截止時間；換算為 **10 月 7 日 14:47:19 至 10 月 12 日 02:05:02 EDT**，時區 America/New_York（UTC−04:00），相隔 **107.30 小時**。本案例取代早期 README 約 34 小時的快照，但不代表期間持續完整取樣。

來源是被 git 忽略的本機 SQLite 歷史 `data/home.sqlite`，由先前執行的 `homenet check`、`path`／`ipv6`、`capacity` 與 `bloat` 保存。本次使用唯讀 SQLite URI、`query_only` 與單一 read transaction；**沒有為了製作此案例執行新網路量測或負載測試**。匯出的是摘要統計與去識別時間線，並非逐封包原始樣本。完整歷史與本機 log 未公開。

## 快照如何產生

在 repository 根目錄執行：

```sh
python -B scripts/export-home-incident.py --through 2026-10-12T06:05:02Z --output docs/evidence/home-incident.json
```

[匯出程式](../scripts/export-home-incident.py) 只讀取截止時間以前的既有列，並記錄程式來源的 SHA-256。此 2026 年 10 月範圍明確使用 EDT，與執行主機時區無關。SSID、MAC／BSSID、使用者／室友識別、地址、目標名稱、原始例外文字與秘密均不匯出；公開目標只有不附對照表的代稱。沒有遷移 schema 或寫入來源資料庫。

每筆時間線的外部值是兩個外部目標中，**有資料的 TCP 連線 p50 之平均**，不是合併封包後的中位數。缺值保留 `null`，並保留有效目標數。基準是排序後零起算 `floor(n × 0.1)` 的值，此處 **21.95 ms**；高於基準加 50 ms，即約 **71.95 ms**，標為慢樣本。時段至少需要兩個慢檢查，之後兩個連續非慢檢查才確認恢復；間隔超過 15 分鐘則以未觀察結束的方式關閉。結束時間是最後一個慢樣本，不是精確的實際恢復時間。這是報告規則，並非根因偵測器。

## 對照結果與修正後的 IPv6 分母

| 對照 | 偵測時段內 | 偵測時段外 | 解讀 |
|---|---:|---:|---|
| IPv4 有回應、任一目標缺少可用 IPv6 結果的批次 | **9／9** | **0／46** | 只顯示所選目標的關聯，不代表全網 IPv6 可用性。 |
| 明確 IPv6 連線嘗試未成功的目標列 | 18 | 0 | 舊收集程式沒有得到成功連線的 p50。 |
| 舊 `no IPv6 address` 目標列 | 27 | 0 | 沒有取得可用 IPv6 地址／結果，未區分 AAAA 資料不存在與解析失敗。 |
| 容量測量批次 | 0 | 80 | 沒有對應的時段內／外容量比較。 |
| 路徑最大增量規則標在接取側的批次 | 9／9 | 46／47 | 是待查範圍，不是實體佇列位置的診斷。 |

**「9／9」計算的是至少一個目標符合缺失條件的批次**，不是九個封包丟失，也不是已證實九次全網中斷。九批共 45 個目標紀錄：18 個明確連線未成功、27 個舊版無地址結果。後者不能改稱已確認 DNS 故障或 IPv6 傳輸失敗。快照中時段外 230 個目標紀錄都有雙協定回應；缺失時段另計，避免只比較成功樣本而讓 IPv6 看似更快。沒有記錄應用程式地址競速／回退或實際媒體流量。

80 次容量測量全部在時段外：77 次有下載數值，中位數 **276.45 Mbps**；80 次有上傳估計值，中位數 **40.54 Mbps**。三次下載測量失敗並保留缺值，其中兩次分類為 HTTP 429。失敗探測不等於可用頻寬為零。下載值是 client 讀到的 payload bytes 除以階段時間；上傳值是 **client 產生／送出的 payload 估計**，未經遠端接收端確認 goodput。兩者均不等於申裝線速，也不能直接當成 lab 的 iperf 接收端吞吐量。

保存的路徑規則在 **55／56** 次追蹤把最大增量標在接取側，另一次標在家用路由器側。時段內 terminal effective latency 中位數為 197 ms，時段外 17 ms。ICMP 控制平面回應、無回應 hop、路由與向後最小值規則限制了定位能力，不能因此證明某個 ISP 佇列已滿。

14 次既有主動測試都有雙方向傳輸階段。保存的增量是 **外部 TCP 在負載時的 p95 減去前一個 idle p50**，中位數為下載 **112.24 ms**、上傳 **67.59 ms**。下載階段閘道 p50 的中位數為 **24.5 ms**，各階段閘道 p95 的中位數為 **112.5 ms**，支持繼續調查負載相關延遲與可能的本地因素。短時間主動負載不能證明自發多小時平台的原因；其「idle」階段也不證明其他居家流量不存在。

## 假設與仍需的證據

| 假設 | 支持觀察 | 缺少的證據／狀態 |
|---|---|---|
| 共用鏈路排隊／bufferbloat | 持續外部平台，既有主動傳輸時延遲增加。 | 時段內沒有被動利用率或容量對照，沒有路由器佇列計數與居家 CAKE 比較。**未確認。** |
| 接取路徑／ISP 壅塞或路由因素 | 外部延遲升高，路徑規則標出接取側增量。 | 沒有 ISP 遙測，探測規則不能區分設備或政策。**未確認。** |
| Wi-Fi、路由器或量測主機因素 | 閘道尾部／丟包，既有下載負載時閘道延遲升高。 | 沒有有線對照、airtime／retry 資料或同步主機負載。時段中位數低不能排除。**未確認。** |
| IPv6 傳輸／路由或地址解析因素 | 時段內抽樣的 IPv6 缺失與 IPv4 回應並存。 | 舊版無地址列沒有 DNS 回覆／錯誤細節，也沒有封包或應用回退紀錄。**未確認。** |
| 某台裝置備份／上下載 | 這類流量可能產生負載相關延遲。 | 沒有裝置利用率或介入對照。**沒有指認任何裝置或人。** |

## 已做處置與尚未做處置

**已完成：** 保存原有收集與負載測試；以固定範圍重算數字、分開觀察與假設、釐清舊 IPv6 結果、保留測量失敗，並產生可重算的去識別快照。

**尚未完成：** 本案例沒有記錄修改家用路由器策略、擺位、DNS、IPv6 設定或部署 CAKE。沒有受控裝置停止／啟動、有線對照、ISP 確認或通話品質前後驗證。之後抽樣延遲較低是觀察，**不是本專案已修好網路的證據**。參數化 Linux CAKE 實驗只提供機制證據；依居家平台校準 lab 不等於獨立居家驗證。

## 驗證計畫——本次未執行

1. 未來再次發生時，先在可存取範圍記錄被動 WAN 利用率、client／路由器負載與介面計數，和檢查時間對齊。確認哪個方向繁忙，不從延遲直接猜測。
2. 可行時用相同目標與協定比較有線／Wi-Fi，保留閘道尾部與主機負載。
3. 分開保存 IPv6 地址解析、TCP 成功／未成功與未探測狀態，涵蓋多個固定地址及具名目標。歷史資料維持原有模糊性，不回填猜測的 DNS 原因。
4. 取得設備管理方式與適當測試時段後，一次測一項介入，記錄利用率／吞吐量及可比較的延遲窗口，重複並恢復設定。負載測試或居家 CAKE 修改屬未來工作，本次分析沒有執行。
5. 另外驗證真實通話，記錄應用／媒體品質及背景吞吐量。改善需要多次前後對照，不只一個恢復樣本。

現階段可支持的是可重算的故障紀錄與較明確的調查方向；資料尚未確認 bufferbloat、特定室友／裝置、DNS 故障、ISP 故障或居家網路已修復。
